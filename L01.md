## Ejercicio 1: Alta Cohesión, Bajo Acoplamiento y Single Responsibility Principle (SRP)

### Contexto
Un sistema de comercio electrónico procesa órdenes de compra. La clase actual realiza la validación, el cálculo de montos con impuestos, la persistencia en base de datos y el envío de notificaciones por correo electrónico dentro de un solo método.

### Código con Problemas (*Code Smell*)
```java
public class OrderProcessor {

    public void processOrder(String itemId, int quantity, double price, String customerEmail) {
        // Validacion
        if (quantity <= 0 || price <= 0) {
            throw new IllegalArgumentException("Cantidad y precio deben ser mayores a cero.");
        }

        // Calculo de negocio
        double total = quantity * price;
        double tax = total * 0.18;
        double grandTotal = total + tax;

        // Persistencia
        System.out.println("Conectando a DB...");
        System.out.println("Guardando orden de " + itemId + " por un total de: $" + grandTotal);

        // Notificacion
        System.out.println("Enviando correo a " + customerEmail + " confirmando la compra.");
    }
}
```

### Instrucciones para el Estudiante
1. Identifique todas las responsabilidades distintas que actualmente asume la clase `OrderProcessor`.
2. Rediseñe la solución separando las responsabilidades en clases con **Alta Cohesión** (`TaxCalculator`, `OrderRepository`, `NotificationService`).
3. Refactorice `OrderProcessor` para que colabore con estas abstracciones, logrando un **Bajo Acoplamiento** y respetando el **SRP**.

## Ejercicio 2: Ley de Demeter y Principios KISS / YAGNI

### Contexto
Un módulo de gestión de envíos consulta la ciudad del cliente navegando a través de múltiples objetos anidados (`Customer -> Company -> Address -> City`). Además, un desarrollador previo incluyó lógica hipercompleja y parámetros para "futuros escenarios" que nunca se han requerido.

### Código con Problemas (*Code Smell*)
```java
class Address {
    private String city;
    public String getCity() { return city; }
    public void setCity(String city) { this.city = city; }
}

class Company {
    private Address address;
    public Address getAddress() { return address; }
}

class Customer {
    private Company company;
    public Company getCompany() { return company; }
}

public class ShippingService {

    // Violacion de la Ley de Demeter (acoplamiento por navegacion en cadena)
    public String getCustomerCity(Customer customer) {
        return customer.getCompany().getAddress().getCity();
    }

    // Violacion de YAGNI/KISS: Metodo sobreingeniado preparado para funcionalidades hipoteticas
    public double calculateComplexShipping(Customer customer, double weight, String mode, boolean isHoliday, String customStrategyCode) {
        if (customStrategyCode != null && customStrategyCode.equals("V1")) {
            return weight * 1.5 + (isHoliday ? 20.0 : 5.0);
        } else if ("AIR".equals(mode)) {
            return weight * 3.0;
        } else {
            return weight * 1.0;
        }
    }
}
```

### Instrucciones para el Estudiante
1. Aplique la **Ley de Demeter** (Principio de Mínimo Conocimiento) de modo que `ShippingService` le solicite directamente la ciudad a `Customer`, evitando la llamada encadenada `getCompany().getAddress().getCity()`.
2. Elimine la sobreingeniería del cálculo de envío aplicando **KISS** y **YAGNI**, simplificando la firma del método y la lógica al escenario real que necesita el negocio.

## Ejercicio 3: Principio DRY y Duck Typing en Java

### Contexto
En Java (lenguaje de tipado estático estricto), el *Duck Typing* no existe de forma nativa. Sin embargo, su equivalente semántico ("si camina como pato y suena como pato, se trata como tal") se logra mediante **Interfaces** o **Polimorfismo**. En este escenario hay duplicación evidente de código de formateo (**DRY**) y ausencia de una abstracción común para tipos de exportación similares.

### Código con Problemas (*Code Smell*)
```java
class PDFReportExporter {
    public void exportPDF(String content) {
        System.out.println("=== INICIO DEL DOCUMENTO ===");
        System.out.println("Formateando encabezado estandar...");
        System.out.println("Contenido PDF: " + content);
        System.out.println("=== FIN DEL DOCUMENTO ===");
    }
}

class HTMLReportExporter {
    public void generateHTML(String content) {
        System.out.println("=== INICIO DEL DOCUMENTO ===");
        System.out.println("Formateando encabezado estandar...");
        System.out.println("Contenido HTML: " + content);
        System.out.println("=== FIN DEL DOCUMENTO ===");
    }
}

public class ReportManager {
    // Codigo duplicado para procesar exportadores especificos
    public void printPDF(PDFReportExporter pdf, String text) {
        pdf.exportPDF(text);
    }

    public void printHTML(HTMLReportExporter html, String text) {
        html.generateHTML(text);
    }
}
```

### Instrucciones para el Estudiante
1. Elimine la duplicación de bloques de encabezado y pie de página en los reportes aplicando el principio **DRY**.
2. Diseñe una interfaz `ReportExporter` para simular **Duck Typing** mediante polimorfismo, permitiendo que `ReportManager` acepte cualquier exportador con un único método genérico.

## Ejercicio 4: SOLID - Open/Closed Principle (OCP)

### Contexto
Un procesador de pagos utiliza un bloque condicional `if-else` para determinar la pasarela según el tipo de pago. Cada vez que el negocio agrega un nuevo método (ej. Yape, Plin, PayPal), se requiere abrir y modificar la clase central.

### Código con Problemas (*Code Smell*)
```java
public class PaymentProcessor {

    public void processPayment(String type, double amount) {
        if (type.equalsIgnoreCase("CREDIT_CARD")) {
            System.out.println("Procesando $" + amount + " con Tarjeta de Credito.");
        } else if (type.equalsIgnoreCase("DEBIT_CARD")) {
            System.out.println("Procesando $" + amount + " con Tarjeta de Debito.");
        } else if (type.equalsIgnoreCase("PAYPAL")) {
            System.out.println("Procesando $" + amount + " via PayPal.");
        } else {
            throw new IllegalArgumentException("Metodo de pago no soportado: " + type);
        }
    }
}
```

### Instrucciones para el Estudiante
1. Explique por qué esta implementación viola el principio **OCP**.
2. Refactorice la estructura mediante el patrón **Strategy** o el uso de una interfaz `PaymentMethod`, de tal forma que agregar un nuevo método de pago consista únicamente en crear una nueva clase, sin modificar `PaymentProcessor`.

## Ejercicio 5: SOLID - Liskov Substitution Principle (LSP)

### Contexto
Un sistema administra archivos de texto. El cliente asume que cualquier subclase de `Document` puede guardarse. Sin embargo, al introducir `ReadOnlyDocument`, este lanza una excepción no esperada al invocar `save()`, rompiendo el contrato explícito de la clase padre.

### Código con Problemas (*Code Smell*)
```java
import java.util.List;

class Document {
    protected String data;

    public void open() {
        System.out.println("Abriendo documento...");
    }

    public void save() {
        System.out.println("Guardando cambios en el documento...");
    }
}

class ReadOnlyDocument extends Document {
    @Override
    public void save() {
        // Violacion de LSP: Rompe las expectativas del cliente lanzando excepcion
        throw new UnsupportedOperationException("Error: Un documento de solo lectura no se puede guardar.");
    }
}

public class DocumentClient {
    public static void saveAllDocuments(List<Document> documents) {
        for (Document doc : documents) {
            doc.save(); // Se rompe el programa en tiempo de ejecucion
        }
    }
}
```

### Instrucciones para el Estudiante
1. Explique por qué `ReadOnlyDocument` violenta el **Principio de Sustitución de Liskov**.
2. Rediseñe la jerarquía de clases e interfaces (ej. separando `Readable` y `Writable`) para garantizar que todas las subclases sean verdaderamente sustituibles por sus abstracciones sin generar excepciones inesperadas.

## Ejercicio 6: SOLID - Interface Segregation (ISP) & Dependency Inversion (DIP)

### Contexto
Una interfaz monolítica ("gorda") obliga a las clases a implementar operaciones que no soportan (**ISP**). Asimismo, un controlador de alto nivel instancia directamente una implementación concreta con `new`, imposibilitando la sustitución o creación de pruebas unitarias (**DIP**).

### Código con Problemas (*Code Smell*)
```java
// Violacion de ISP: Interfaz sobrecargada con responsabilidades no agrupadas
interface MultiFunctionDevice {
    void print(String doc);
    void scan(String doc);
    void fax(String doc);
}

// Una impresora basica solo imprime, pero se ve forzada a implementar metodos no soportados
class BasicPrinter implements MultiFunctionDevice {
    @Override
    public void print(String doc) {
        System.out.println("Imprimiendo: " + doc);
    }

    @Override
    public void scan(String doc) {
        throw new UnsupportedOperationException("Funcion de escaneo no soportada.");
    }

    @Override
    public void fax(String doc) {
        throw new UnsupportedOperationException("Funcion de fax no soportada.");
    }
}

// Violacion de DIP: El modulo de alto nivel depende directamente de la clase concreta
public class OfficeController {
    private BasicPrinter printer; // Acoplamiento fuerte a clase concreta

    public OfficeController() {
        this.printer = new BasicPrinter(); // Instanciacion directa (Hardcoded)
    }

    public void printDocument(String doc) {
        printer.print(doc);
    }
}
```

### Instrucciones para el Estudiante
1. Segregue la interfaz `MultiFunctionDevice` en interfaces de grano fino (`Printer`, `Scanner`, `Fax`) respetando el principio **ISP**.
2. Modifique `OfficeController` para que dependa de la abstracción `Printer` y aplique **Inyección de Dependencias** a través del constructor respetando el principio **DIP**.
