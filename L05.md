# Laboratorio Diseño y Arquitectura: Tarjetas CRC, Paquetes y Atributos de Calidad

**Herramientas:** Papel/pizarra o herramienta de diagramado (draw.io, PlantUML, Mermaid, Lucidchart, etc.)  
**Modalidad:** A realizarse con los equipos del curso  
**Objetivo:** Modelar las responsabilidades de un sistema mediante tarjetas CRC, organizarlo en paquetes UML e identificar los requisitos arquitectónicamente significativos y los atributos de calidad que guiarán su arquitectura.

---

## Caso de Estudio: AgroSmart - Plataforma de Agricultura Inteligente

Una cooperativa agrícola del valle de Ica agrupa a **120 pequeños y medianos productores** de uva, espárrago y palta. Actualmente, cada productor decide cuándo regar, fertilizar o fumigar basándose en su experiencia, lo que genera desperdicio de agua (un recurso escaso en la zona), pérdidas por plagas detectadas tarde y dificultades para cumplir con los requisitos de trazabilidad que exigen los compradores internacionales.

La cooperativa desea construir **AgroSmart**, una plataforma que funcione de la siguiente manera:

- Cada **productor** registra sus **parcelas** (ubicación, área, tipo de cultivo y fecha de siembra). Una parcela pertenece a un único productor, pero un productor puede tener varias parcelas.
- En cada parcela se instalan **sensores** (humedad del suelo, temperatura, humedad relativa y conductividad eléctrica del suelo) que envían **lecturas** periódicamente a la plataforma a través de un **gateway** instalado en el campo.
- La plataforma compara las lecturas con **umbrales** configurados por cultivo y, cuando un valor sale de rango, genera una **alerta** para el productor.
- Algunas parcelas cuentan con **válvulas de riego** automatizadas. El productor puede programar **riegos** (fecha, hora y duración) o activarlos manualmente desde la aplicación.
- El productor puede registrar **actividades agrícolas** (riego, fertilización, fumigación, cosecha) indicando fecha, insumos utilizados y cantidades, lo que conforma el **cuaderno de campo** de la parcela.
- El **administrador de la cooperativa** gestiona los usuarios, los tipos de cultivo con sus umbrales y los sensores/gateways instalados.

## Pregunta 1: Tarjetas CRC y Paquetes

### 1) Tarjetas CRC

A partir del caso de estudio, identificar las **clases candidatas** del sistema y elaborar una **tarjeta CRC** (Clase - Responsabilidades - Colaboradores) por cada una.

Recordar que:

- Una **responsabilidad** es algo que la clase **sabe** (información que mantiene) o **hace** (acción que realiza).
- Un **colaborador** es otra clase con la que debe interactuar para cumplir alguna de sus responsabilidades.
- Las clases candidatas suelen surgir de los **sustantivos** del caso; las responsabilidades, de los **verbos**.

Formato de referencia de una tarjeta:

```
+---------------------------------------------------------------+
| Clase: Parcela                                                |
+-------------------------------------+-------------------------+
| Responsabilidades                   | Colaboradores           |
+-------------------------------------+-------------------------+
| Conocer su ubicación y área         |                         |
| Conocer su cultivo y fecha siembra  | Cultivo                 |
| Conocer a su productor              | Productor               |
| ...                                 | ...                     |
+-------------------------------------+-------------------------+
```

Se pide:

1. Elaborar **al menos 8 tarjetas CRC**.
2. Presentar las tarjetas en un **gráfico** (diagrama o imagen) en el que se distingan claramente las tres secciones de cada tarjeta y se muestren las **colaboraciones** entre ellas (por ejemplo, ubicando las tarjetas que colaboran cerca unas de otras o uniéndolas con flechas).
3. Simular con las tarjetas (*role-playing*) el siguiente escenario y describir brevemente la secuencia de colaboraciones:

> *Un sensor de humedad envía una lectura de 12 % en una parcela de espárrago cuyo umbral mínimo es 18 %. El sistema debe generar una alerta y notificar al productor.*

> **Tip:** Si durante la simulación una clase no tiene a quién pedirle la información que necesita, falta un colaborador o una responsabilidad. Si una clase acumula demasiadas responsabilidades, considerar dividirla.

### 2) Paquetes del proyecto

Organizar las clases identificadas en **paquetes** que agrupen elementos con alta cohesión y bajo acoplamiento entre sí.

Se pide:

1. Elaborar un **diagrama de paquetes en UML** que muestre:
   - Los paquetes del sistema y las clases que contiene cada uno.
   - Las **dependencias** entre paquetes (flechas punteadas `<<use>>`).
2. Verificar que el diagrama **no tenga dependencias cíclicas** entre paquetes. Si las hay, explicar cómo las resolverían.
3. Justificar brevemente (2 a 3 líneas por paquete) el criterio usado para agrupar las clases.

## Pregunta 2: Requisitos Arquitectónicamente Significativos y Atributos de Calidad

Luego de una primera reunión con la cooperativa, el alcance de AgroSmart se amplió. A continuación se detalla el listado de requisitos levantados.

### Requisitos funcionales

| ID | Requisito |
|----|-----------|
| RF01 | El sistema debe permitir al productor registrar, editar y dar de baja sus parcelas. |
| RF02 | El sistema debe recibir y almacenar las lecturas de los sensores enviadas por los gateways cada 5 minutos. |
| RF03 | El sistema debe generar una alerta cuando una lectura sale del rango configurado para el cultivo y notificar al productor por **WhatsApp**. |
| RF04 | El sistema debe permitir programar riegos y activar/desactivar las válvulas de riego de forma remota. |
| RF05 | El sistema debe permitir que el productor tome una **foto de una hoja** desde la aplicación móvil y que un **modelo de IA de visión** identifique si presenta alguna plaga o enfermedad. |
| RF06 | El sistema debe consultar diariamente el **pronóstico del clima** de un servicio externo (por ejemplo, SENAMHI u OpenWeather) y suspender automáticamente los riegos programados si se pronostica lluvia. |
| RF07 | El sistema debe generar, mediante un **modelo de IA predictivo**, una **recomendación de riego** semanal por parcela en base a las lecturas históricas, el clima y el tipo de cultivo. |
| RF08 | El sistema debe permitir registrar las actividades agrícolas del cuaderno de campo y exportarlo en PDF. |

### Requisitos no funcionales

| ID | Requisito |
|----|-----------|
| RNF01 | La aplicación móvil debe permitir registrar actividades y fotos **sin conexión a internet** y sincronizarlas automáticamente cuando se recupere la conexión (muchas parcelas tienen cobertura móvil intermitente). |
| RNF02 | El sistema debe soportar la recepción de lecturas de hasta **5 000 sensores** simultáneamente, con la posibilidad de crecer a 50 000 sensores cuando se incorporen otras cooperativas de la región. |
| RNF03 | Una alerta crítica (por ejemplo, humedad del suelo por debajo del mínimo) debe notificarse al productor en **menos de 1 minuto** desde que se recibe la lectura. |
| RNF04 | Si la plataforma no está disponible, las válvulas deben seguir ejecutando la última programación de riego recibida. |
| RNF05 | Solo se debe poder activar una válvula de riego con un usuario autenticado y autorizado sobre esa parcela. |
| RNF06 | Debe ser posible **cambiar el proveedor del modelo de IA** o del servicio de clima sin modificar la lógica de negocio del sistema. |

### Se pide

1. **Requisitos arquitectónicamente significativos (ASR):** Del listado anterior, seleccionar los requisitos que consideren **arquitectónicamente significativos**. Para cada uno:
   - Justificar por qué es significativo para la arquitectura (alto impacto en la estructura del sistema, alto riesgo, difícil de cambiar más adelante, involucra sistemas externos, etc.).
   - Indicar qué **decisión arquitectónica** podría derivarse de él (por ejemplo: un patrón, un estilo, un componente o una tecnología).

   Presentar el resultado en una tabla con el siguiente formato:

   | ID | ¿Por qué es arquitectónicamente significativo? | Posible decisión arquitectónica |
   |----|------------------------------------------------|---------------------------------|
   |    |                                                |                                 |

   Indicar también **al menos 2 requisitos que NO consideren arquitectónicamente significativos** y explicar por qué.

2. **Atributos de calidad:** A partir del caso y de los requisitos, determinar los **atributos de calidad** relevantes para AgroSmart (por ejemplo: disponibilidad, rendimiento, escalabilidad, seguridad, modificabilidad, interoperabilidad, usabilidad, etc.). Para cada atributo:
   - Indicar de qué requisitos (RF/RNF) o de qué parte del caso se deriva.
   - Redactar un **escenario de atributo de calidad** con sus seis partes: *fuente del estímulo, estímulo, artefacto, entorno, respuesta y medida de la respuesta*.

3. **Priorización y *trade-offs*:** Ordenar los atributos de calidad identificados según su importancia para el negocio y explicar **al menos 2 conflictos** (*trade-offs*) entre ellos. Por ejemplo, ¿qué tensión existe entre RNF03 y RNF06?

## Entregables

Un documento (PDF o Markdown en el repositorio del equipo) que contenga:

1. El gráfico de las tarjetas CRC y la descripción del escenario simulado.
2. El diagrama de paquetes UML con la justificación de cada paquete.
3. La tabla de requisitos arquitectónicamente significativos y los requisitos descartados.
4. Los escenarios de atributos de calidad y su priorización con los *trade-offs*.
